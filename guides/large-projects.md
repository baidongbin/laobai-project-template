# 大型项目按需扩展

沿用 Lite、Standard 的底座和状态约定，不增加第三档初始化预设。本指南供模板使用者参考，不默认复制进业务项目，也不要求一次创建以下全部结构。

## 按场景直接使用

大型项目通常选择 Standard 加按需扩展。在 AI 工具中打开目标项目，替换指令中的路径与目标后发送。模板仓库只读，业务目标目录才是接入对象；不要把本指南整份复制成目标项目 AGENTS。

<a id="new-project"></a>
### 新开发大型项目

```text
模板仓库：<模板仓库的绝对路径>
目标项目：<目标项目的绝对路径>
预设：Standard + 按需大型项目扩展
项目目标：<主要用户、核心场景、范围和已确认的技术约束>

请读取模板仓库 guides/initialize.md 与 guides/large-projects.md，
为目标项目建立协作底座和首阶段实施计划。
先检查目录，已有内容增量接入，不覆盖现有文件。
根据已确认需求提出必要的领域与模块边界，重大未决问题明确说明。
architecture.md 只描述当前实现；没有代码时写尚未实现。
初始目标架构放任务计划或其按需设计附件，不强制建立版本目录。
将首阶段拆成可验收任务单元，明确跨模块依赖、集成顺序和验收条件。
只取必要的模块规则、领域架构和环境模板；实际模块尚未建立时，
不创建虚假的代码入口或局部 AGENTS，不默认采用微服务或多 Agent 并行。
保持项目状态、任务状态和文档核对入口各自唯一，没有提交核对就保持未核对。
检查链接与正文是否能支持后续接手，报告实际检查和待决定事项。
本次只建立协作底座和首阶段计划，不实现业务、不安装依赖、
不初始化 Git、不提交、推送或部署。
```

有影响实施正确性的未决设计时先解决，再授权具体任务。实现落地后同步当前架构与任务记录，不提前将目标方案写成已实现。

<a id="existing-project"></a>
### 已有大型项目

```text
模板仓库：<模板仓库的绝对路径>
目标项目：<目标项目的绝对路径>
参考预设：Standard + 按需大型项目扩展
首个试点领域：<指定领域，或填写“先检查后提出建议”>

请读取模板仓库 guides/adopt.md 与 guides/large-projects.md，
为目标项目增量接入协作规范。
先检查项目规则、Git 状态、文档入口及顶层模块，建立阅读地图，
再按领域核实必要的代码、配置、测试和已确认需求，不无差别扫描全仓。
已有职责清楚、内容可用的文档原位复用，不因文件名不同而迁移。
先完善全局导航及状态入口，再选一个领域补齐模块规则、架构详情和验证入口；
已有任务继续沿用，补充跨模块依赖、集成验收与接续点，不建立竞争进度记录。
领域详情确需拆分时移动正文，原处保留概要和链接，不保留两份权威正文。
环境说明按真实需要补充服务顺序、配置来源、数据和端口隔离。
保留可信文档基线、覆盖和缺口；局部领域核对不能代表全项目已核对。
既有规则、文档职责或打包脚本存在实质冲突时，说明原约定、差异、
影响与最小方案；未决部分等待确认，继续不受影响的工作。
按局部任务和跨模块任务检查阅读入口，报告试点结果和未覆盖领域。
本次不改业务实现、不重排源码、不安装依赖、不初始化 Git、
不提交、推送或部署，也不自动启动多 Agent。
```

先验证一个领域的接入效果，再按明确范围逐步推广。记录本轮覆盖边界，不把“全局入口已整理”描述为所有领域都已核对。

## 可直接填写的模板

- [模块级 AGENTS](../extensions/large/module-AGENTS.md.template)：只补充模块特有规则。
- [领域架构](../extensions/large/domain-architecture.md.template)：职责、契约、不变量与代码验证入口。
- [环境与隔离](../extensions/large/environment.md.template)：重建前提、服务顺序和资源分配；也可合并进现有开发说明。
- 跨模块任务使用 [单文件计划](../extensions/plan.md.template) 或 [目录式计划](../extensions/plan/README.md.template)，填写新增的可选协作章节。

按 [扩展落位说明](../extensions/README.md) 复制所需文件、去掉 `.template` 后缀并填写占位内容；实际路径与示例不同须重算链接。不自动复制整套扩展，不新增全局状态入口。

## 何时扩展

当多个服务、领域或技术栈需要独立开发、验证或发布，且现有入口已难以表达边界时，逐项扩展。代码行数、文档数量或一次复杂任务本身不构成扩展理由。

| 实际问题 | 最小调整 |
|---|---|
| 架构说明难以局部阅读 | `docs/architecture.md` 保留系统总览，按领域拆出详情并直接链接 |
| 不同模块的开发规则明显不同 | 在对应模块按需增加局部 AGENTS，根入口只保留共用规则 |
| 跨模块任务难以接续 | 任务主记录明确各模块范围、依赖顺序、接续点及集成验收 |
| 环境依赖个人机器状态 | 在开发说明补齐依赖版本、配置来源、测试数据与重建步骤 |
| 多人或多 Agent 相互干扰 | 按需隔离工作区、端口、数据和输出，明确集成负责人或角色 |

## 文档与模块边界

保留现有 `docs/architecture.md` 路径及其总览职责，不再增加一份同等权威的根 ARCHITECTURE。拆分时移动详细正文，原处保留概要和链接；不要强制采用微服务、领域分层或新的源码目录命名。

每个需要独立理解的模块说明职责、对外契约、允许的依赖、关键不变量以及代码和验证入口。不要求为每个函数建立文档；局部决策能在架构文档说清时，不单独建立 ADR。

只将已确认且仍适用的约束写成不变量。说明为什么必须保持、如何核验；可执行检查存在时链接测试或 lint，尚未自动验证时说明限制，不把目标架构写成当前实现。

## 局部规则与任务接续

局部 AGENTS 只记录模块特有约束与阅读入口，不复制根规则、项目状态或架构正文。先核对实际使用工具对作用域、导入及优先级的支持，再用新会话验证；不假设所有工具合并规则的方式一致。参考 [工具接入](tool-access.md)。

已指定任务时直接读取其主记录及必要依据，不固定要求逐级通读 README、架构总览和全部领域资料。跨模块工作在主记录说明每部分的输入、产出、前置依赖和集成验收；只有确需独立执行时才拆子任务，子任务状态各自维护，主记录仅保留关联与总体阻塞。

并行执行需先明确允许修改的范围、接口约定和集成顺序。多工作区仍须隔离共享数据库、端口和外部服务；记录实际执行者或集成角色，不凭模板预设多人协作，也不自动启动子 Agent。

任务结束仍归入 `plans/archive/`，区分完成、取消与被替代，不建立另一套 HANDOFF、SESSION 或 CURRENT_STATUS。

## 环境与验证

从已注明的必要工具开始，应能按文档获得依赖、配置本地环境并运行相关模块。使用项目已选定的依赖管理和锁定文件，列出外部服务、测试数据来源及清理方式，敏感值只说明获取渠道。

优先沿用真实原生命令。多个检查确需编排时再增加统一入口，说明适用模块、前置条件、执行范围及副作用；不默认创建 setup、lint、verify 空脚本。局部检查通过不代表跨模块集成通过，完整验证也不代替生产验收。

## 状态与迁移验收

项目进度由 README 或已建立的 roadmap 统一导航，长期要求、当前架构、决策与任务记录各有归属。文档核对仍在既有唯一入口汇总，可按领域列覆盖范围和缺口；若不能在同一基线核对完整既有范围，就保留旧基线，不用局部检查推进全局结论。

扩展遵循 [迁移指南](lite-to-standard.md)：不破坏既有路径与任务 ID，不复制权威正文，不因拆分刷新核对基线。

验收时选一个局部任务和一个跨模块任务，检查新会话能否找到直接入口、识别依赖与未核实内容、给出正确验证方式。未实际运行的环境重建、并行隔离或跨工具接续，保持未验证并说明限制。
